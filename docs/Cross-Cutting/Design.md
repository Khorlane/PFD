Simulation --- Design

## 1. Purpose

This project is a C++ simulation of a small, fully operating food
distribution business named **\<business name>**.

The objective is to simulate the company as an integrated business
rather than as isolated departmental models. The simulation advances
through the live calendar and models operational days, shifts,
transactions, physical inventory movement, employees, customers,
suppliers, accounting, cash, equity, and capital investment.

The company name is configurable. **\<business name>** is the
default simulation company name.

The initial simulation start date is also configurable.

------------------------------------------------------------------------

## 2. Simulation Philosophy

The simulation will model actual business operations and the
dependencies between departments.

``` text

   |

   |
Delivery
   |

   |

```

The supply-side chain is:

``` text
   |
```

Accounting observes and records the financial effects of the operational

## 3. Simulation Clock

The engine will use actual calendar dates and timestamps.

The simulation must distinguish between:

-   Calendar date/time
-   Business/operating date
-   Operating phase
-   Accounting period

This is necessary because warehouse operations frequently cross
midnight.

Example:

``` text
Monday 17:00   Orders being processed
Monday 23:30   Picking
Tuesday 02:15  Truck loading
Tuesday 04:00  Truck departure
Tuesday 07:30  Customer delivery
Tuesday 08:00  Office opens
```

The Tuesday early-morning warehouse activity belongs to the fulfillment
cycle generated by Monday's customer orders.

The simulator should eventually support operations such as:

``` cpp
simulation.runDay();
simulation.runDays(numberOfDays);
simulation.runWeek();
simulation.runUntil(date);
```

Internally, processing will be timestamp/event based.

## 6. Sales and Customer Order Schedule

Sales personnel take customer orders Monday through Friday.

The normal fulfillment relationship is:

  Order Taken   Primary Warehouse Fulfillment   Expected Delivery
  ------------- ------------------------------- -------------------
  Monday        Monday evening/night            Tuesday
  Tuesday       Tuesday evening/night           Wednesday
  Wednesday     Wednesday evening/night         Thursday
  Thursday      Thursday evening/night          Friday
  Friday        Sunday evening/night            Monday
  Saturday      No orders taken                 ---
  Sunday        No orders taken                 ---

A Friday customer order is therefore held for the Sunday warehouse cycle
and is expected to be delivered Monday.

A Monday order is normally fulfilled Monday night and delivered Tuesday.

The model may later support exceptions such as delayed orders, partial
shipments, emergency orders, or expedited deliveries.

Customer deliveries normally occur Monday through Friday.

Typical order-to-delivery flow:

``` text
Monday

        |

        |

        |
Monday night picking
        |
Truck loading
        |
Tuesday morning departure/delivery
        |

        |
```

``` text

        |

        |

        |

```

Transportation is modeled separately from warehouse staffing because
trucks may depart during the overnight warehouse cycle and remain on
delivery routes after warehouse shift boundaries.

## 10. Master Files --- No Database

The simulation will **not use a relational database**.

Persistent business master data will be stored in simple binary master
files.

Every master record has a unique, permanent business key.

Examples:

-   Customer Number
-   Employee Number
-   Product Number
-   Supplier Number
-   Sales Representative Number
-   Truck Number
-   General Ledger Account Number
-   Fixed Asset Number

Initial master files include:

``` text
CUSTOMER.MST
EMPLOYEE.MST
PRODUCT.MST
SUPPLIER.MST
SALESREP.MST
TRUCK.MST
ACCOUNT.MST
FIXEDASSET.MST
```

Additional master files may be added as the design grows.

## 11. Every Master File Has an Index

**Design decision: every master file has its own index file.**

Example:

``` text
data/masters/

    CUSTOMER.MST
    CUSTOMER.IDX

    EMPLOYEE.MST
    EMPLOYEE.IDX

    PRODUCT.MST
    PRODUCT.IDX

    SUPPLIER.MST
    SUPPLIER.IDX

    SALESREP.MST
    SALESREP.IDX

    TRUCK.MST
    TRUCK.IDX

    ACCOUNT.MST
    ACCOUNT.IDX

    FIXEDASSET.MST
    FIXEDASSET.IDX
```

The master file contains the actual binary records.

The index contains:

``` text
Unique Key -> Physical Master File Record Location
```

Conceptually:

``` cpp
struct IndexEntry
{
    uint32_t key;
    uint64_t fileOffset;
};
```

A lookup such as:

``` cpp
auto customer = customerFile.find(10245);
```

will:

1.  Look up Customer Number 10245 in `CUSTOMER.IDX`.
2.  Obtain the physical byte offset.
3.  Seek directly to that position in `CUSTOMER.MST`.
4.  Read the customer record.

For this small-business simulation, the complete index may be loaded
into memory when the master file is opened.

The actual master records remain in the binary master file.

## 12. Generic Master File Services

A reusable master-file component should support operations similar to:

``` cpp
template<typename Key, typename Record>
class MasterFile
{
public:
    bool create(const std::string& filename);
    bool open(const std::string& filename);

    bool insert(const Record& record);
    bool update(const Record& record);

    std::optional<Record> find(const Key& key) const;

    void forEach(/* callback */);

    bool validateIndex();
    bool rebuildIndex();

    void close();
};
```

Required capabilities include:

-   Unique-key insertion
-   Random lookup by key
-   Record update
-   Sequential processing
-   Index validation
-   Index rebuild
-   Persistent storage

Physical deletion of historically referenced master records should
normally be avoided. An entity such as a customer, employee, supplier,
or product should generally be marked inactive instead.

This preserves historical transaction integrity.

## 13. Key Generation

Unique keys will be persistent and must not be accidentally reused.

A control file can maintain next-number values.

Example:

``` text

```

Possible internal numbering:

``` text

Product Number        1+
Supplier Number       1+
```

``` text
Customer      C00001234

Supplier      S00000117
Sales Order   SO00015287
Invoice       INV00087431
```

The permanent underlying key can remain numeric.




## 26. Randomness and Reproducibility

The simulation will include controlled stochastic behavior.

Examples:

-   Whether a customer orders
-   Order size
-   Product mix
-   Employee absence
-   Supplier delay
-   Supplier fill rate
-   Customer payment timing
-   Truck breakdown
-   Product damage

Randomness must be reproducible using a configurable random seed.

Example:

``` cpp
config.randomSeed = 123456;
```

The same starting state and random seed should produce the same
simulated outcome.

This enables controlled scenario comparison.
